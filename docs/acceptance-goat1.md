# Goat step 1 (pod 1 to host): acceptance

This checklist covers the plan in `docs/superpowers/plans/2026-11-11-goat-step1-pod-to-host.md`, on branch `goat`. Task 1 (G1-01), Task 9 (G1-02 to G1-05 and G1-11) and Task 10 (G1-06 to G1-09) are recorded so far; each entry was recorded in the commit that adds it.

A ticked box means a run recorded the evidence named on that line. It doesn't mean the whole requirement was met, so each line says what was measured and where it falls short. A check that could not run is recorded as unknown.

## G1-01: version pairing

- [x] **G1-01.** Two sessions of the Python binding in `apex-sapient:4.2.0` (zenoh 1.10.2), A and B, each connected over mutual TLS to a router from `eclipse/zenoh:1.9.0` (`zenohd v1.9.0`, arm64, `zenoh/router-pairing.json5`), exchange data through it. A publishes and declares the token; B subscribes and queries liveliness, so each sample and token had to cross the router. The default of `FABRIC_ZENOH_IMAGE` stays `eclipse/zenoh:1.9.0`.
  - `docker compose -f docker-compose.pairing.yml run --rm probe` printed `PAIRING OK put-sub liveliness`: B received A's StatusReport bytes unchanged on `probe/a`, and B's `alive("probe/live/*")` returned A's token `probe/live/x`.
  - With `PROBE_WAIT_RESTART=1` and `docker compose -f docker-compose.pairing.yml restart zenohd` five seconds in, both sessions reported transport False then True. The probe then printed `PAIRING OK put-sub liveliness` and `PAIRING OK after router restart`, exit code 0. It made no new subscribe or declare call after the restart, so B's subscription and A's token worked again through the router. The probe doesn't tell the binding's replay of declarations apart from any other way the router could have learnt them.
  - Falls short: two sessions with one certificate (`radar.p1.h1`), one subscriber, one token and one StatusReport-sized payload, on one Docker network on one arm64 host. The router has no access control, and one restart was tried. An earlier version of the probe used one session, which delivers its own samples locally and proved nothing about the router; that run is not evidence. Nothing was measured on a router built for x86-64, under load, with several certificates, or with the access lists of Task 2 onward.

- [x] **G1-02, tracks and alerts up.** The host fusion node logged `<- detection_report` from the pod's fusion node (`f0000001`) and `<- alert f0000001 ALERT_TYPE_INFORMATION "new track ..."`, one alert. The host recorder held 141 records in the first run (93 in the README run); every `anchor` was the pod's (`18214b1a...`) or the host fusion node's (`b005ae3a...`), and no `msg.node_id` was the radar's, the camera's or the vehicle's. The host recorder subscribes to three key patterns only, `*/telemetry/sapient/*/v2/*/*`, `*/ack/*/sapient/v2/*/*` and `*/task/*/sapient/v2/task/*`, so a key of any other shape would not be seen. It sees only what the fabric router lets the `host-recorder` certificate read. Liveliness tokens and queries are not covered. - [x] **G1-05, access on the live routers.** Both routers restarted with `RUST_LOG=zenoh::net::routing::interceptor=trace`; `emulators/probe_access.py` in one-off containers put or subscribed with a chosen certificate, while a subscriber whose certificate may read the key counted the probe's own samples. The rule for the evidence: a put was denied when the probe subscriber got 0 probe samples and the router's trace has no `authorized` line for that certificate's put on that key; the `unauthorized` lines support it. The reason is in `zenoh/src/net/routing/interceptor/access_control.rs` at tags `1.9.0` and `1.10.2`, function `action`: it tries each subject that the certificate matches in turn, logs `unauthorized` for each subject that denies, and stops at the first subject that allows with one `authorized` line. So a denied action logs one `unauthorized` line for each matching subject and no `authorized` line, and an allowed action can log `unauthorized` lines before its `authorized` line. (1) The pod's slot certificate putting on `<host fusion anchor>/task/p1/sapient/v2/task/<pod fusion node ID>`: subscriber got 0 probe samples; the fabric router logged `CN=18214b1a34e3c722d1cac283b272a62c is unauthorized to Put (ingress)` twice (two subjects) and never `authorized` (the saved trace lines are shortened by a `sed` that writes the certificate's common name as `CN=`). (2) The host fusion certificate putting on `<pod anchor>/telemetry/sapient/p1/v2/alert/<pod fusion node ID>`: 0 probe samples, `unauthorized` twice. (3) The host recorder certificate subscribing to `**`: 0 samples in 15 s and `unauthorized to Declare Subscriber (ingress) on **`; the same certificate on `*/telemetry/sapient/*/v2/*/*` received 31 to 33 samples in 15 s. (4) In the pod, the radar certificate putting on the camera's up key: 0 probe samples (only the camera's own 3 status reports), the pod router logged `unauthorized` once. In the first run each denied put also had a control: the allowed certificate on the same key reached the subscriber (1 probe sample), and the receiving node dropped the probe's status report (the pod bridge counted `bad_kind`; the host and pod fusion nodes logged `does not match the owner of its key`). The routers went back to `info`, and the pod bridge forwarded again after both router restarts.
  - Falls short: four cases, one key each, `put` and `declare_subscriber` only; no liveliness token, query or delete was probed, and no other slot of the pools was tried. The denial evidence is the router's trace text and a 15 s subscriber window. The router also logged `unauthorized to Put (ingress)` on the key for the subscriber's certificate when it subscribed, with no put sent: in the same file, `compute_keyexpr_cache` works out the decision for all nine actions (query, reply, put, delete, subscriber, queryable, liveliness token, liveliness query, liveliness subscriber) when it caches a client's key expression, and each goes through `action`, which logs. A later message that uses the cache logs one line starting `Using cached result:`. The counts in the README filter by the putting certificate's common name, so they leave the subscriber's lines out, but they read the router's whole log since it started, not only the seconds of the probe; in cases 1, 2 and 4 a live service holds the same certificate common name as the probe (the pod bridge, the host fusion node, the radar). The first run tied each trace line to the probe by its time.

## G1-06 to G1-09: outages, an old task, and a join

Run on 2026-11-12 UTC with `docker-compose.goat1.yml` (project `apex-goat1`), on top of commit `8db9951`, on the same arm64 host and images as G1-02. Each live check ran twice: once from a script that also logged the times and the counters, and once as README steps 7 to 9, pasted with steps 1 to 6 into one zsh. The commands and what the README run printed are in README.md, section "Goat step 1: pod 1 to host". The times below are from the scripted runs, UTC.

- [x] **G1-06, short outage.** On the rig 60 s after `dg up`, `docker network disconnect apex-goat1_mesh apex-goat1-pod-bridge-1` ran at 00:11:57 and `docker network connect` at 00:12:27. The pod bridge logged `pod-bridge-1  | 00:12:06 pod-bridge: fabric router lost` 9 to 10 s after the disconnect, and `pod-bridge-1  | 00:12:29 pod-bridge: fabric router back` 2 s after the connect. In the 30 s of the outage, `dg logs --since 30s radar camera vehicle fusion-node` had 0 lines with `lost` or `cannot reach`, and the pod fusion node logged 6 `<- detection_report` lines from the radar and the camera. After the connect, the host fusion node logged 3 `<- detection_report` lines in 25 s and 0 `<- registration ` lines in 60 s. The bridge's counters:
  - before: `pod-bridge-1  | 00:11:57 pod-bridge: forwarded {'up': 68, 'down': 5}; dropped {}`
  - during: `pod-bridge-1  | 00:12:27 pod-bridge: forwarded {'up': 79, 'down': 5}; dropped {'other_side_down': 22}`
  - after: `pod-bridge-1  | 00:12:57 pod-bridge: forwarded {'up': 112, 'down': 7}; dropped {'other_side_down': 25}`

  `stale_task` stayed at 0: the host's `look_at` task `8G7344`, sent at 00:12:16 during the outage, never reached the bridge, so nothing was held back and the pod fusion node never got it. The README run gave the same results: 0, 6, 2 and 0, and `other_side_down` 18 during and 26 after.
  - Falls short: two 30 s outages, each made by taking the bridge off the `mesh` network; a loss of the pod network, a router restart during the outage, and packet loss short of a cut were not tried. The host's hold of the pod fusion node is not logged, so the check shows only that the host did not remove it and asked for no registration. Between the counter line at 00:11:57 and the loss, the bridge's `up` counter rose by 11 (68 to 79, with the disconnect in that window); whether those messages arrived was not checked. A task sent from the host during the outage is lost, not delivered late.
