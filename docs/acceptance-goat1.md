# Goat step 1 (pod 1 to host): acceptance

This checklist covers the plan in `docs/superpowers/plans/2026-11-11-goat-step1-pod-to-host.md`, on branch `goat`. Task 1 (G1-01) and Task 9 (G1-02 to G1-05 and G1-11) are recorded so far; each entry was recorded in the commit that adds it.

A ticked box means a run recorded the evidence named on that line. It doesn't mean the whole requirement was met, so each line says what was measured and where it falls short. A check that could not run is recorded as unknown.

## G1-01: version pairing

- [x] **G1-01.** Two sessions of the Python binding in `apex-sapient:4.2.0` (zenoh 1.10.2), A and B, each connected over mutual TLS to a router from `eclipse/zenoh:1.9.0` (`zenohd v1.9.0`, arm64, `zenoh/router-pairing.json5`), exchange data through it. A publishes and declares the token; B subscribes and queries liveliness, so each sample and token had to cross the router. The default of `FABRIC_ZENOH_IMAGE` stays `eclipse/zenoh:1.9.0`.
  - `docker compose -f docker-compose.pairing.yml run --rm probe` printed `PAIRING OK put-sub liveliness`: B received A's StatusReport bytes unchanged on `probe/a`, and B's `alive("probe/live/*")` returned A's token `probe/live/x`.
  - With `PROBE_WAIT_RESTART=1` and `docker compose -f docker-compose.pairing.yml restart zenohd` five seconds in, both sessions reported transport False then True. The probe then printed `PAIRING OK put-sub liveliness` and `PAIRING OK after router restart`, exit code 0. It made no new subscribe or declare call after the restart, so B's subscription and A's token worked again through the router. The probe doesn't tell the binding's replay of declarations apart from any other way the router could have learnt them.
  - Falls short: two sessions with one certificate (`radar.p1.h1`), one subscriber, one token and one StatusReport-sized payload, on one Docker network on one arm64 host. The router has no access control, and one restart was tried. An earlier version of the probe used one session, which delivers its own samples locally and proved nothing about the router; that run is not evidence. Nothing was measured on a router built for x86-64, under load, with several certificates, or with the access lists of Task 2 onward.

## G1-02 to G1-05 and G1-11: the step 1 rig

Run on 2026-11-11 UTC with `docker-compose.goat1.yml` (project `apex-goat1`), on top of commit `08ef7c2`, on one arm64 host under Colima: pod router `eclipse/zenoh:1.10.2`, fabric router `eclipse/zenoh:1.9.0`, all other services `apex-sapient:4.2.0`. The commands and what they printed are in README.md, section "Goat step 1: pod 1 to host". All 11 services ran. At bring-up, 45 s after `dg up`, the routers' logs had no line with `error` or `panic`; that was measured once, not after the later steps.

- [x] **G1-02, tracks and alerts up.** The host fusion node logged `<- detection_report` from the pod's fusion node (`f0000001`) and `<- alert f0000001 ALERT_TYPE_INFORMATION "new track ..."`, one alert. The host recorder held 141 records in the first run (93 in the README run); every `anchor` was the pod's (`18214b1a...`) or the host fusion node's (`b005ae3a...`), and no `msg.node_id` was the radar's, the camera's or the vehicle's. The only top-level node IDs in the host recorder's records were `f0000001` and `f0000002`.
  - Falls short: one pod, a scripted scenario, a few minutes of traffic; the number of tracks was not measured. The check reads the host's recorder and the host fusion node's log; it doesn't compare each forwarded payload with the bytes the pod fusion node sent (the unit tests of the pod bridge do that). The host recorder subscribes to three key patterns only, `*/telemetry/sapient/*/v2/*/*`, `*/ack/*/sapient/v2/*/*` and `*/task/*/sapient/v2/task/*`, so a key of any other shape would not be seen. It sees only what the fabric router lets the `host-recorder` certificate read. Liveliness tokens and queries are not covered. Only the top-level `node_id` of each message was compared, so a sensor's ID inside a message body would not be seen.
- [x] **G1-03, registration.** The pod fusion node accepted the radar, the camera and the vehicle (through `bridge-node`) with `acceptance=True`, then registered upward. The host fusion node logged `<- registration f0000001 "fake fusion node" [FUSION_NODE]`, and the pod fusion node logged `<- registration_ack f0000002 -> f0000001 acceptance=True`, about 6 s after start.
  - Falls short: one pod, one host fusion node, each started once from a clean state, and once after a restart of the host fusion node (below). Registration with several host anchors in `FABRIC_HOST_ANCHORS` was not tried.
- [x] **G1-04, a task down.** The host's first `look_at` came 40 s after start. The chain, from the first run (location fields cut):

- [x] **G1-05, access on the live routers.** Both routers restarted with `RUST_LOG=zenoh::net::routing::interceptor=trace`; `emulators/probe_access.py` in one-off containers put or subscribed with a chosen certificate, while a subscriber whose certificate may read the key counted the probe's own samples. The rule for the evidence: a put was denied when the probe subscriber got 0 probe samples and the router's trace has no `authorized` line for that certificate's put on that key; the `unauthorized` lines support it. The reason is in `zenoh/src/net/routing/interceptor/access_control.rs` at tags `1.9.0` and `1.10.2`, function `action`: it tries each subject that the certificate matches in turn, logs `unauthorized` for each subject that denies, and stops at the first subject that allows with one `authorized` line. So a denied action logs one `unauthorized` line for each matching subject and no `authorized` line, and an allowed action can log `unauthorized` lines before its `authorized` line. (1) The pod's slot certificate putting on `<host fusion anchor>/task/p1/sapient/v2/task/<pod fusion node ID>`: subscriber got 0 probe samples; the fabric router logged `CN 18214b1a... is unauthorized to Put (ingress)` twice (two subjects) and never `authorized`. (2) The host fusion certificate putting on `<pod anchor>/telemetry/sapient/p1/v2/alert/<pod fusion node ID>`: 0 probe samples, `unauthorized` twice. (3) The host recorder certificate subscribing to `**`: 0 samples in 15 s and `unauthorized to Declare Subscriber (ingress) on **`; the same certificate on `*/telemetry/sapient/*/v2/*/*` received 31 to 33 samples in 15 s. (4) In the pod, the radar certificate putting on the camera's up key: 0 probe samples (only the camera's own 3 status reports), the pod router logged `unauthorized` once. In the first run each denied put also had a control: the allowed certificate on the same key reached the subscriber (1 probe sample), and the receiving node dropped the probe's status report (the pod bridge counted `bad_kind`; the host and pod fusion nodes logged `does not match the owner of its key`). The routers went back to `info`, and the pod bridge forwarded again after both router restarts.
  - Falls short: four cases, one key each, `put` and `declare_subscriber` only; no liveliness token, query or delete was probed, and no other slot of the pools was tried. The denial evidence is the router's trace text and a 15 s subscriber window. The router also logged `unauthorized to Put (ingress)` on the key for the subscriber's certificate when it subscribed, with no put sent: in the same file, `compute_keyexpr_cache` works out the decision for all nine actions (query, reply, put, delete, subscriber, queryable, liveliness token, liveliness query, liveliness subscriber) when it caches a client's key expression, and each goes through `action`, which logs. A later message that uses the cache logs one line starting `Using cached result:`. The counts in the README filter by the putting certificate's common name, so they leave the subscriber's lines out, but they read the router's whole log since it started, not only the seconds of the probe; in cases 1, 2 and 4 a live service holds the same certificate common name as the probe (the pod bridge, the host fusion node, the radar). The first run tied each trace line to the probe by its time.

Brought down after.

  - Falls short: one restart of the host fusion node. A restart of the pod fusion node, of the pod bridge, or a router outage longer than a second was not tried here (Task 10 does the outage checks).
