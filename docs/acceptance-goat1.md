## G1-01: version pairing

- [x] **G1-01.** Two sessions of the Python binding in `apex-sapient:4.2.0` (zenoh 1.10.2), A and B, each connected over mutual TLS to a router from `eclipse/zenoh:1.9.0` (`zenohd v1.9.0`, arm64, `zenoh/router-pairing.json5`), exchange data through it. A publishes and declares the token; B subscribes and queries liveliness, so each sample and token had to cross the router. The default of `FABRIC_ZENOH_IMAGE` stays `eclipse/zenoh:1.9.0`.
  - `docker compose -f docker-compose.pairing.yml run --rm probe` printed `PAIRING OK put-sub liveliness`: B received A's StatusReport bytes unchanged on `probe/a`, and B's `alive("probe/live/*")` returned A's token `probe/live/x`.
  - With `PROBE_WAIT_RESTART=1` and `docker compose -f docker-compose.pairing.yml restart zenohd` five seconds in, both sessions reported transport False then True. The probe then printed `PAIRING OK put-sub liveliness` and `PAIRING OK after router restart`, exit code 0. It made no new subscribe or declare call after the restart, so B's subscription and A's token worked again through the router. The probe doesn't tell the binding's replay of declarations apart from any other way the router could have learnt them.
  - Falls short: two sessions with one certificate (`radar.p1.h1`), one subscriber, one token and one StatusReport-sized payload, on one Docker network on one arm64 host. The router has no access control, and one restart was tried. An earlier version of the probe used one session, which delivers its own samples locally and proved nothing about the router; that run is not evidence. Nothing was measured on a router built for x86-64, under load, with several certificates, or with the access lists of Task 2 onward.

## After the final review

The final review read the whole branch (base `0cca505`, head `2c949fe`). It found no critical issue: the access lists match the code key by key, the bridge's key mapping and the host's link agree, and the earlier rigs are untouched. Its findings, and what was done:

- **An over-long site in a key ended the host fusion node (fixed, `9c1e655`).** `fabric_keys.parse` checked the site only against `[a-z0-9]+`, with no limit of length, while `key_for` refuses a key longer than `MAX_KEY_BYTES`. So a sample with a site of 200 characters, which any slot holder may publish below its own anchor, passed `parse`, the host stored the site in the node's route, and `key_for` raised when the host built its reply key from it; nothing caught the error, and the host fusion node ended, again at each restart while the token lived. A site is now 1 to 32 characters of `[a-z0-9]` (`MAX_SITE_CHARS` in `emulators/fabric_keys.py`, and the registry check of `emulators/slots.py`), and `parse` and `parse_live` also refuse a key longer than `MAX_KEY_BYTES`. With that cap every kind of every class has a key for any site that parses (a unit test builds them all for a site of 32 characters).
- **The fabric link's `send` could raise, and the node logged sends that did not happen (fixed, `9c1e655`).** `FabricFusionLink.send` now catches the `ValueError` of `key_for`, logs the kind and the node, and returns `False` whenever it sent nothing (no route, a kind with no key, or a key it cannot build). `FakeFusionNode.send` writes its `->` line only when the link did not return `False`; the other links return nothing and keep their behaviour.
- **The pod bridge could run on broken, or stop, with no log line (fixed, `bfb7ec6`).** `PodBridge.run` waited only on the two sessions' `closed` events. It now ends when any of its tasks ends: a closed session logs one line that names the session and says the bridge stops, and returns; any other task that ends is logged with its exception, which is raised, so the process ends with an error and compose starts it again. A lost router is still handled by `on_transport`, and one bad sample still does not end the bridge.
- **Node ID ownership deviates from design 4.4 (recorded, not changed).** The host binds a node ID to the anchor of the first key or token that names it, before decoding or validation, and never releases it. The controller ruled that this is recorded in this step and fixed before step 5; see "Node ID ownership" under the known limits.
- **The record missed two limits (recorded).** The host's state grows with each node ID that a slot names, with no cap or expiry, and the subscription queues are not bounded; and the validator's time window of 0.9 s behind and 0.1 s ahead is the real age limit of a message, which needs clocks that agree. Both are now under the known limits, with three smaller points: every peer may also declare a queryable and reply on any anchor's keys; a sensor's alert would carry the sensor's node ID in its body to the host (G1-02); a task from the future passes the bridge but not the pod fusion node's validator.
- **Smaller points (fixed).** The host recorder's line for an undecodable payload now holds `kind`, `node_id`, `anchor` and `site` in fabric mode, as design 4.8 says; in pod mode it is unchanged (`4b0143d`). `goatgen.py --frozen-routers` now counts a router file that does not exist as a change, and refuses the pod alias `fusion-node`, whose environment name would be that of the pod's fusion node (`e02a289`). The help texts of `--status-interval` and `--node-hold-seconds` name transport `fabric` too (`9c1e655`).

## Known limits and open items for step 4

The reviews of Tasks 1 to 11 and the final review found these points. Task 12 checked each against the code at `c6a2db1` or the evidence named; after the final review each was checked again against the code at `e02a289`, and the line numbers below are those of `e02a289`. None of the review fixes closes one of them.

- **A lost link is noticed late.** The pod bridge notices the loss of the fabric router only when its session times out: 9 to 10 s after the disconnect in Task 10, and 10 s in the final run (`task-12-readme-run.txt`). What the pod sends in that time counts as forwarded, and whether it arrived was not checked, so it may be lost with no count. Each task the host sent during an outage was lost, not delivered late: `8G7344` in Task 10 and `4BXK8S` in the final run, two cases, both sent after the bridge had noticed the loss. The run after the review fixes lost a third, `536K0X`, in the same way.
- **A fusion node takes a detection from a node that has not registered.** `_on_detection` in `emulators/fake_fusion_node.py` (line 579) checks no registration. `_on_status` (line 563) also makes an entry for a node that has not registered. The host made a track from the pod fusion node's traffic before the node registered three times: after the host restart of Task 9 (`new track GDDKMQ from f0000001` at 23:42:16, registration at 23:42:19), after the long outage of Task 10 (`new track 7HEGEK` at 00:16:08), and after the long outage of the final run (`new track DHV7EM from f0000001` at 01:30:30, registration at 01:30:33). The run after the review fixes made it a fourth time (`new track XB2DA3 from f0000001` at 02:22:34, registration at 02:22:37).
- **A location that is not a number passes.** Apex's validator, with the fusion node's options, returns no error for a detection at `x = nan` or `x = inf` (`task-12-nan-check.txt`). The fusion node then keeps a track at that location: if it has no track it makes a new one there, and otherwise it moves the first track in its list there: every comparison of a NaN distance is false, so `min(...)` returns the first track (line 586) and the gate test `> GATE_M` does not reject it (line 587) (`emulators/fake_fusion_node.py`).
- **Nothing revokes a slot.** A slot certificate stays valid for as long as its CA is trusted. Zenoh has no revocation list (`docs/goat-context.md` 2.7), and taking an alias out of the registry removes neither its certificate nor its access (G1-09).
- **Reading is not limited by slot.** The fabric router's rule `peer-r-scoped` lets every mutual-TLS peer subscribe and query on `*/**` (`router-fabric.json5`). This is goat's scoped read, so any certified peer may read below any anchor (G1-10). The same rule lets every peer declare a queryable and reply on any anchor's keys (its `messages` hold `declare_queryable` and `reply`). This is goat's rule; queries are a non-goal of step 1.
- **No Zenoh session ID is set.** `ZenohSession.open` in `emulators/zenoh_io.py` sets no `id`, and neither router file has one, so every client and router has a random ID. goat's ADR 1041 (status "Proposed") asks for a fixed router ID for each host and for source info on the publishers goat owns. Separately, goat's command line tool sets a publisher's session ID to its slot anchor; goat's code credits that to ADR 1039, and ADR 1041 describes it only as context (`docs/goat-context.md` 2.11). Open for step 4.
- **The goat client was tried in one form.** goat's client does not verify the router's TLS name (from goat's source, G1-10). Only `goat sub` ran. A profile from a signed bundle, a portal and a key service do not exist in the rig, so `goat profile init`, `goat doctor` and `goat sub --decode` or `--open` were not tried.
- **A task from the future passes the bridge.** The bridge's age check (`_age` in `emulators/pod_bridge.py`, line 169) subtracts the task's time from the clock, so a task with a time in the future has a negative age and is forwarded. No test covers it. It passes only the bridge: the pod fusion node then drops a task more than 0.1 s ahead of its clock (see the next point).
- **The validator's time window is the real age limit, and it needs clocks that agree.** Both fusion nodes check each message with Apex's validator and the options `messageTimestampRange: [-0.9, 0.1]` (`VALIDATION_CONFIG` in `emulators/fake_fusion_node.py`, line 100; check `message_timestamp_reasonable`), which reject a message whose timestamp is more than 0.9 s behind or more than 0.1 s ahead of the receiver's clock (`_check_message_timestamp_reasonable` in Apex's `sapient_apex_server/validate_proto.py`, read in the image `apex-sapient:4.2.0`: the message's time minus the receive time must lie between the two numbers). Since Task 7 the pod fusion node applies this to everything from above (`_parent_loop`, line 659). So a task 4 s old, which the bridge forwards (the unit test of G1-08), is then dropped by the pod fusion node as invalid (read from the code; no test sends one through both); the bridge's 5 s limit is only an outer bound. On a real mesh (step 4), a clock difference or a delay near one second makes each side reject the other's traffic.
- **The bridge's token cleanup can stop early.** When the pod router is lost, `on_transport` (`emulators/pod_bridge.py`, line 189) calls `undeclare_token` for each node in a loop with no guard; one call that raises stops the loop and leaves the list of nodes uncleared. While the fabric link is down the bridge drops the pod's messages before it notes them, so it removes its own token after 30 s (`expire_presence`, line 181), on a session that is away (seen in G1-07).
- **Node ID ownership is "first key wins", not "the anchor that registered it".** This is a deviation from the design, section 4.4, which says: "A node ID belongs to the anchor that registered it." The code does less. The fabric link binds a node ID to the anchor of the first key that names it (`_accept` and `_learn` in `emulators/fabric_link.py`, lines 144 and 67), before the payload is decoded or validated, and also from a bare liveliness token (`node_of_live_key`, line 86). A route is never released, also not when the fusion node removes the node after the hold time; it is lost only when the host restarts. Effect: a holder of any fabric slot certificate that is first to publish, below its own anchor, a sample that names the pod fusion node's ID owns that ID at the host, and the host then drops the real pod's traffic. After each host restart the race is open again. In step 1 the other slots are our own (the host recorder, the goat test client). It must be fixed before a second pod (step 5): bind ownership on an accepted registration, or take the node-to-anchor map from the registry. Downward kinds make it worse with more than one host: `task` and the acknowledgements name the node they go to, so another host's task to the pod fusion node could set that node's route to the wrong anchor; only upward kinds should set a route. The rig has one host and no foreign slot holder, so neither case was seen.
- **The host's state is not bounded.** One slot can name any number of node IDs below its own anchor. Each one adds an entry to the fabric link's `routes` (and, for a node ID another anchor holds, to its `_refused` set), to the fusion node's `validators`, `nodes` and `_token_alive`, and, for each token, a hold or request timer (`_hold_timers`, `_pending_requests`) and a registration request (`emulators/fake_fusion_node.py`, lines 402 to 478). A hold timer and a pending request remove their own entries when they end or are cancelled, and hold expiry removes the `validators` and `nodes` entries of a node that goes. Nothing removes an entry of `_token_alive`, `routes` or `_refused`, and nothing caps any of them. The queues of `ZenohSession.subscribe` (`emulators/zenoh_io.py`, line 126) are not bounded either; only the pod bridge's buffers are (`QUEUE_LIMIT`).
- **The host can task only the pod fusion node.** The bridge passes down only messages for node IDs that it has sent upward (`_known`, line 150), and publishes them on the fusion node's down key (line 157). Only the fusion node's traffic goes up, so a sensor in the pod can't be tasked from the host directly, and the sensors' own acknowledgements stay in the pod.
- **The scale of the evidence.** One pod, one host, one arm64 machine under Colima, Docker networks in place of a mesh, a test CA made by the generator, and runs of minutes.
- **Step 4 itself.** No procedure is known that gives a system other than the founder a slot identity on a goatlite (`docs/goat-context.md` 5.2). A goatlite is a LAN goatnet. Its fabric router is Zenoh 1.9.0, the version that check G1-01 covers for our binding.
