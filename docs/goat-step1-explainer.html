The idea in one minute

A site that must detect and stop drones uses sensors from many makers: radars, cameras and others. The sensors must report what they see in one common format. Software must join these reports into one picture. People at a higher site must see that picture and send orders back.

We build this in levels. A pod is a small group of sensors at the edge, with its own software that joins their reports. A host is the next level up. It collects the pictures of several pods. An external host belongs to a partner, who gets only the data that we release.

What step 1 showsOne pod sends its joined picture to one host, and takes orders from it, over a network that follows the rules of the goat network. Each party can write only in its own space. The pod continues to work when the link to the host is lost.
A way to picture itThink of a branch office and a head office. The branch (the pod) does its own work every day. One clerk at the door (the pod bridge) carries the manager's summary to the head office (the host) and brings orders back. The clerk does not open the envelopes, but checks each address. Every person has a badge, and can put papers only into the locker with their own number.

Three things to know first

Step 1 puts three existing things together. Select each one.

SAPIENT

What it is. SAPIENT is a standard for the messages between sensors, effectors and the software that joins their data. Dstl, a UK government laboratory, developed it. The British Standards Institution publishes it as BSI Flex 335. We use version 2.0.

A way to picture it. It is a set of standard forms. Every sensor fills in the same form in the same way, whoever made the sensor.

What matters here. Each device is a node with a node ID. A sensor is a node. The software that joins reports is a fusion node. A node must register before it sends data. Each message is one protobuf structure, SapientMessage. Select a message kind:

Registration

The standard carries these messages over TCP. Dstl's reference software for that is the Apex middleware. Our earlier work (stages 1 to 4 in README.md) moved the same messages onto Zenoh.

Zenoh

What it is. Zenoh is an open source protocol for publish and subscribe. A program publishes data on a key. Other programs subscribe to keys and receive the data. A router passes the data between them.

A way to picture it. It is a wall of pigeonholes, and each one has an address. You put a paper into one pigeonhole. Other people ask for "all pigeonholes that match this pattern".

What matters here.

  • A key is a path, for example h1/p1/fusion/up/detection_report.
  • A subscriber gives a pattern, called a key expression. * stands for exactly one part of the path. ** stands for any number of parts.
  • A router can check a certificate before it lets a program write or read a key. This is how the rules below are enforced.
  • A liveliness token is a key that exists only while its owner is connected. Others use it to know that a node is present.

Try a key expression

The names in capitals are short forms. RADAR, CAMERA and FUSION stand for node IDs. POD and HOST stand for the two anchors that the goat part explains. This tester knows * and ** only.

    The goat network

    What it is. goat is an open source project of United States Army Europe and Africa. One goat network, a "goatnet", has four parts: a private mesh network between machines (WireGuard), a Zenoh data fabric, an identity service, and a certificate authority (CA). One nation or organisation operates one goatnet.

    A way to picture it. It is a building with badges and numbered lockers. The badge is a certificate. The locker number is an anchor.

    The rules that matter here.

    • Identity is a slot. The operator makes a pool of slots before anyone joins. Each slot has an anchor: 32 characters, made from a hash. A new member gets the certificate of a free slot. The router does not restart.
    • You write only below your own anchor. Every key that a member writes starts with its anchor, for example 18214b1a…/telemetry/…. So a reader always knows who wrote the data.
    • Every certified member may read. But a subscription to everything (**) is refused. A reader must name at least the top level, as in */telemetry/….
    • A denial is silent. The router drops a forbidden message and tells the sender nothing.
    • Other nations get release lanes. Data for a partner goes to special keys and through a separate router. This is step 6, not step 1.
    Important for step 1Step 1 does not use a real goatnet. It uses our own stand-in: a stock Zenoh router of the version that goat uses (1.9.0), with access rules that we generate by goat's rules, on Docker networks. A real goatnet comes in step 4. One real goat tool is used: goat's command line client reads our data in one check.

    When things fail, and when a sensor joins

    A pod at the edge can lose its link to the host. Step 1 tested a short loss and a long loss. It also tested a new sensor that joins a running pod.

    A short loss of the link (30 seconds)
    • 0 sThe link between the pod bridge and the fabric router is cut.
    • 10 sThe bridge notices the loss. Inside the pod nothing changes: sensors report, the fusion node makes tracks.
    • 30 sThe link returns. The bridge connects again by itself.
    • afterThe host receives tracks again. It did not remove the pod, and the pod did not register again.

    The host keeps a node for a hold time (120 seconds by default) after its presence token is gone. A task that the host sent during the loss was lost. It was not delivered late.

    A long loss of the link (40 seconds, with the hold time set to 20 seconds)
    • 0 sThe link is cut.
    • 10 sThe bridge notices the loss. The host stops seeing the pod's presence token, and its hold time starts.
    • 30 sThe hold time ends. The host removes the pod fusion node from its list.
    • 40 sThe link returns.
    • 44 sThe host sees the pod again and sends a task: "register again". The pod registers, and the host accepts it.
    A new sensor joins with no router restart
    • 1The pool of the pod router has 8 slots from the start. Slots 0, 1 and 2 are in use. Slot 3 is free.
    • 2We give the name radar2 to slot 3 in one file and run the generator. It makes one new certificate. The router files do not change.
    • 3The new radar starts with that certificate. The pod fusion node accepts its registration and takes its detections.
    • 4The router's start time is the same as before. It did not restart.

    The earlier stage 4 pod could not do this. A new sensor needed a change of the router's access list and a restart.

    What step 1 showed

    Step 1 has eleven acceptance checks. All passed, in two whole runs from newly made certificates. The record is docs/acceptance-goat1.md. The saved outputs are in docs/evidence/goat1/.

    CheckIn plain wordsResult
    G1-01Our Zenoh library (1.10.2) works with a router of goat's version (1.9.0), also after the router restarts.pass
    G1-02The host receives the pod's tracks and alerts. No raw sensor data is on the fabric: of 6304 records at the host, none holds a sensor's ID.pass
    G1-03The pod fusion node registers with the host, and the host accepts it.pass
    G1-04A task from the host reaches the radar and the camera. The acknowledgement returns to the host.pass
    G1-05Four forbidden actions are denied by the running routers (section 6).pass
    G1-06A short loss of the link: the pod works alone, and the host keeps the pod.pass
    G1-07A long loss: the host removes the pod, then asks it to register again.pass
    G1-08The bridge drops a task that is older than 5 seconds.pass unit test only
    G1-09A new radar joins with a new certificate only. The pod router does not restart.pass
    G1-10goat's own command line tool, built from goat's source, reads the pod's tracks from our fabric router.pass
    G1-11The earlier rigs still work. The unit suite has 454 passing tests.pass
    What step 1 does not show
    • No real goatnet yet. The host side is our stand-in on one machine, with a test CA. Docker networks stand for the mesh.
    • Clocks must agree. Each side rejects a message that is more than 0.9 seconds old. A real network needs synchronised clocks.
    • A lost link is noticed late. It takes 9 to 10 seconds. Messages sent in that time are lost.
    • Who owns a node ID. The host gives a node ID to the first sender that names it. The design asks for more. This must be fixed before a second pod.
    • No way to remove a member. A certificate stays valid. Nothing revokes it.
    • The fusion is a toy. It joins detections that are closer than 100 metres. Real fusion comes in step 2.
