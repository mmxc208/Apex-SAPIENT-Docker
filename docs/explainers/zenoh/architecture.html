Zenoh in one page

Option A: sidecar bridge, Apex retained

Bridge responsibilities

  • Node side: accept the node's TCP connection, read length-prefixed SapientMessages, peek node_id from the first (registration) message, publish each on sapient/v2/<node_id>/up/<type>, declare a liveliness token sapient/v2/live/<node_id>, subscribe to .../<node_id>/down/** and write those back to the socket.
  • Apex side: subscribe to sapient/v2/*/up/** and to live/**. On a new node_id open one TCP connection to Apex's Child port (5020 for v2). Apex binds identity to the connection (ChildConnection._handle_other rejects a node_id mismatch as "hijacked"), so one socket per node is mandatory. Forward Apex's replies to .../down/<type>.
  • Presence: when a node's token drops, close its Apex socket, otherwise Apex keeps a ghost registration. Optionally hold the socket for up to 2 minutes to honour §4.9 without a re-registration, since Apex requires the first message on any new connection to be a registration.
  • QoS: Block on registration, task, alert and acks; Drop allowed on detections; express flag on tasks.
Why not put Zenoh inside Apex instead

ApexServer.serve() only needs receive_some, send_all and aclose on a Trio stream, so a Zenoh-backed stream per node is feasible. The costs are spawning a virtual connection per node from liveliness events, and marshalling Zenoh's synchronous callbacks into Trio (trio.from_thread or a memory channel). Do this only after the sidecar has proved the key design and QoS settings. Apex's single parser token (CapacityLimiter(total_tokens=1)) remains the throughput ceiling either way.

Option B: Zenoh-native pods, host and external host

Where Apex's jobs go

Apex jobOption B owner
Accept connections, forward by node_idZenoh routers (keys)

Key namespace

<host>/<pod>/sapient/v2/<node_id>/up/{registration,status,detection,alert,task_ack,alert_ack,error}
<host>/<pod>/sapient/v2/<node_id>/down/{registration_ack,task,alert_ack,error}
<host>/<pod>/fusion/up/{registration,status,detection,alert}      # pod fusion as a child Fusion_Node
<host>/<pod>/fusion/down/{registration_ack,task}
<host>/fusion/up/{...}                                            # host fusion toward the external host
sapient/v2/live/<node_id>                                         # liveliness tokens
  • Subscriptions: pod fusion h1/p1/sapient/v2/*/up/**; host fusion h1/*/fusion/up/**; external COP h1/fusion/up/**.
  • Payload: the serialised SapientMessage, unchanged, encoding application/protobuf. No length prefix.
  • Only node UUIDs appear in keys; they are fixed-length, so key cardinality equals node count.

Router configuration sketch

Shapes follow DEFAULT_CONFIG.json5 in the Zenoh repo. Values are illustrative; validate against the installed version before use.

{
  mode: "router",
  listen:  { endpoints: ["tls/0.0.0.0:7447"] },
  connect: { endpoints: ["tls/host-router.example:7447"] },   // pod → host; host → external
  scouting: { multicast: { enabled: false }, gossip: { enabled: true } },
  transport: {
    link: { tls: {
      root_ca_certificate: "/etc/zenoh/ca.pem",
      listen_private_key: "/etc/zenoh/pod1.key", listen_certificate: "/etc/zenoh/pod1.pem",
      connect_private_key: "/etc/zenoh/pod1.key", connect_certificate: "/etc/zenoh/pod1.pem",
      enable_mtls: true, verify_name_on_connect: true, close_link_on_expiration: true } },
    unicast: { lease: 5000, keep_alive: 4 }
  },
  access_control: {
    enabled: true, default_permission: "deny",
    rules: [
      { id: "fusion-tasks",  messages: ["put"], flows: ["ingress"], permission: "allow",
        key_exprs: ["h1/p1/sapient/v2/*/down/**", "h1/p1/fusion/down/**"] },
      { id: "node-uplink",   messages: ["put","liveliness_token"], flows: ["ingress"], permission: "allow",
        key_exprs: ["h1/p1/sapient/v2/*/up/**", "sapient/v2/live/*"] },
      { id: "anyone-reads",  messages: ["declare_subscriber","query"], flows: ["ingress"], permission: "allow",
        key_exprs: ["h1/**", "sapient/v2/live/**"] }
    ],
    subjects: [
      { id: "fusion", cert_common_names: ["fusion.p1.h1.example"] },
      { id: "nodes",  cert_common_names: ["radar1.p1.h1.example", "cam1.p1.h1.example", "eff1.p1.h1.example"] }
    ],
    policies: [
      { rules: ["fusion-tasks","anyone-reads"], subjects: ["fusion"] },
      { rules: ["node-uplink","anyone-reads"],  subjects: ["nodes"] }
    ]
  },
  downsampling: [                                    // host router, WAN side only
    { interfaces: ["wan0"], flows: ["egress"], messages: ["put"],
      rules: [ { key_expr: "h1/*/fusion/up/detection", freq: 2.0 } ] }
  ],
  gateway: { south: [ { filters: [ { region_names: ["pod1"] } ] },
                      { filters: [ { region_names: ["pod2"] } ] } ] }   // host router: one subregion per pod
}
Check before useThe ACL key_exprs for a node should ideally be restricted to that node's own node_id, which means one subject per node or a templating step at provisioning. The gateway.south custom form is new in 1.9 and documented tersely; confirm the exact nesting against the installed version.

The §4.11 hierarchy on Zenoh tiers

BSI Flex 335 v2.0 §4.11: a child fusion node "shall publish and receive messages as edge nodes do", registering with node type Fusion_Node and declaring the aggregated detection and tasking capability of its edge nodes. Lower-level raw detections do not cross a level; the child's own detection reports (fused tracks) do. The TCP role rules (top fusion = server, mid-level = client up and server down, edge = client) describe connections, which Zenoh replaces, but the registration relationship between fusion applications still has to exist.

§4.11 elementPod / host / external hostMatch
Edge nodesSensors and effectors in a podSame
Lowest fusion nodePod fusion/COP, registering upward as Fusion_NodeSame
Parent fusion nodeHost fusion/COP, tasking pod fusion as a taskable edge nodeSame
Client/server channels per levelRouter-to-router linksDifferent layer; still need the app-level registration
Only fused output crosses a levelAnything on a matching key crossesEnforce by subscription design (host reads */fusion/**, never */sapient/v2/*/up/detection) and by ACL
Apex and hierarchyApex's ParentConnection forwards fused tracks and alerts to a listener and relays anything received to the DMMs; it does not register with a parent. A conformant child fusion node must itself connect to the parent's Child port and send a registration. Chaining Apex instances does not implement §4.11; the fusion node does.

Stone Soup as the fusion node

What exists (v1.9.1+103)

  • stonesoup.reader.base.DetectionReader and TrackReader abstractions; concrete readers for Kafka, CBOR, YAML, HDF5, AIS, OpenSky, pandas, video; writers for Kafka, CBOR, YAML. Nothing for SAPIENT, raw TCP or Zenoh.
  • KafkaDetectionReader consumes on a background thread into a Queue and yields (timestamp, set[Detection]). This is the template for a Zenoh-backed reader, since eclipse-zenoh delivers samples on its own threads.
  • Trackers in tracker/simple.py (MultiTargetTracker, MultiTargetMixtureTracker), plus particle, PMHT and point-process trackers; predictors, updaters, data associators, initiators, deleters; platform and sensor models; metrics.

Adapter design

  1. Ingress: a SapientDetectionReader(DetectionReader) with a pluggable source: Zenoh subscriber on h1/p1/sapient/v2/*/up/detection, or a TCP client to Apex's Peer port (5001) reading length-prefixed messages. Both feed one queue.
  2. Registry: keep each sensor's Registration and latest StatusReport (location, field of view). Build the sensor's measurement model from them: Cartesian for lat/long/UTM reports, polar bearing–range for range-bearing reports. Only the ENU velocity frame exists in v2.
  3. Conversion: DetectionReport → Detection(state_vector, timestamp, measurement_model, metadata={node_id, report_id, object_info}). Use the message timestamp as measurement time; NTP is mandatory in the standard.
  4. Tracking: standard components, unchanged.
  5. Egress: publish tracks as DetectionReports from the fusion node's own node_id with associated_detection listing source report IDs, on h1/p1/fusion/up/detection. Publish the fusion node's own Registration (type Fusion_Node, aggregated capabilities per §4.11) and periodic StatusReport with a coverage area that updates as sensors come and go.
  6. Tasking: subscribe to h1/p1/fusion/down/task; decompose a task into per-sensor Tasks on .../<node_id>/down/task; relay TaskAcks.
  7. Test harness: sapient_apex_replay can replay a recorded SQLite trial into the TCP source; the fake nodes in Apex-SAPIENT-Docker/emulators exercise the live path.
Design ruleKeep the Zenoh dependency inside the source class. The reader, registry, tracker and egress code must not import zenoh, so the same fusion node runs over Apex/TCP in Option A and natively in Option B.

Decisions needed

  1. Target topology. Single LAN → keep TCP, add TLS. Multi-site → Option A first. Pods/host/external → Option B.
  2. Effector authority. Which certs may publish down/task to an effector: pod fusion, host fusion, human COP only. Encoded in ACL.
  3. Apex's future. In path (A), consumer behind a bridge (B with GUI), or retired.
  4. Zenoh release pin and upgrade policy, given the open router issues.
  5. Stone Soup adapter ownership, needed in every option.
