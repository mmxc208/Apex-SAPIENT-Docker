Goat step 4: a goatlite goatnet, and the step 1 rig on it

Two pieces of work from 2026-11-18 and 19: standing up the goatnet cuaslab with goatlite, then moving the step 1 rig onto it (branch goat-step4-cuaslab). The numbers come from docs/acceptance-goat4.md and from the goatlite assay. Written 2026-11-19. One file, no network needed.

What was done

First, a goatnet. goatlite is goat's way to stand up a whole goatnet on one host. We used it to build cuaslab in a virtual machine on a Mac, and its acceptance suite passed. The "goatlite" tab has the details.

Then, step 4.

Step 1 ran pod 1 and the host against a stand-in fabric router with a test certificate authority. Step 4 moved the same rig, unchanged, onto the real goatlite goatnet cuaslab: the real router, real enrolment through the portal, and real certificates from the goatnet's authority.

The scope the user chose was "move it as it is", done with one overlay compose file. No existing file under emulators/ changed.

Three things worth remembering

  • Mesh and fabric are two different memberships. A mesh peer is a network address. A fabric slot is a certificate and a key prefix. Step 4 used the fabric and not the mesh.
  • Step 4 is "shape C". The whole pod appears on the fabric as one identity, the bridge. ADR 1251 lists this shape as a rejected alternative for the long term.
  • The host does not see the sensors. Only what the pod fusion node produces crosses the bridge.

What goatlite is

goatlite is tutorial 0 of goatcore (docs/tutorials/00-goatlite.md). It stands up a complete goatnet on one host from one file, goatlite.yaml. The tool goatbuilder standup renders the full configuration from that file and then runs the same numbered phases as a real deployment. So a goatlite is a real goatnet, only small: one box, a private certificate authority, and a LAN instead of the internet.

What one box then runs

  • mesh NetBird: management, signal, dashboard, mesh DNS
  • Ory (Kratos and Hydra): people's sign-in and OIDC
  • A private certificate authority; leaf certificates for each service
  • fabric The Zenoh router, mutual TLS on port 7447, with a pool of 1000 slots
  • The portal: registry, certificate minting, grants, enrolment
  • Supporting services: grant-keyd, the onboarding front desk and runner, peer-health, Postgres with backups

How the pieces sit after the stand-up

  • The box is not a mesh peer. A goatlite box only hosts the services. They are served on its LAN address, and the laptop reaches them there.
  • The laptop has a fabric identity first. The founder's certificate lets goat publish and subscribe before any machine is on the mesh. Joining the mesh adds the network identity.
  • Names. Before the mesh join, one line in /etc/hosts; after it, the mesh DNS answers for the zone.
  • Trust. The goatnet has its own root, cuaslab goatlite CA. Each tool must be told to trust it, and each tool reads trust from a different place.
  • No health beats. goat health reports none. A goatlite deploys no health publisher; this is expected.

Three ways to attach a pod

ADRs read, and what each says for a pod

A task from the host to the pod

Which sensors get the task? Today the pod fusion node sends look_at to every registered node that is not mobile. It does not pick by which sensor saw the target. Sensor selection is step 2 work (Stone Soup in the fusion node). No goat ADR covers it; goat's ADRs are about the network and identity, not fusion logic.

The bridge subscribes inside the pod only to the fusion node's upward keys, so a sensor's message never reaches it. Check G4-02 measured the result: 192 host records, none with a sensor's ID as sender or in the content. The pod recorder keeps the sensor data locally.

Why it was built this way

  • Raw detections are many, fused tracks are few, and an edge link may be narrow.
  • goat wants the number of keys on the fabric to stay bounded.
  • In SAPIENT a higher fusion node deals with a child fusion node, not with that node's sensors.

What it costs

  • The host cannot fuse again from raw data.
  • The host cannot check why the pod made a track.
  • The host does not know which sensors exist or whether they are healthy.

Enrolment: how the three identities were made

  1. goat4/enroll.sh checks every target path first and stops before any portal write if one is not a regular file.
  2. It asks the portal for a machine grant for the custodian (quota 5, affiliation cuaslab-lab).
  3. It enrols three machines: pod1-bridge (class POD), host-fusion and host-recorder (class FUSION). The portal answers 201 with a slot ID and a one-time bundle link.
  4. It downloads each bundle, picks the root certificate by parsing and verifying X.509 (not by file name), and checks that all three bundles share one root.
  5. It writes certificates and keys to zenoh/goat4/pki/ and the three slot IDs to zenoh/goat4/goat4.env. Both are git-ignored.

The classes PROCESSOR, SENSOR and EFFECTOR were refused by the portal. 26 tests cover the script against a fake portal on 127.0.0.1.

Different from step 1

  • The router is the goatnet's (zenohd v1.9.0-modified). We do not restart it or read its log.
  • The identities come from the portal and the goatnet's authority. Step 1 used a test authority and a pool of 8.
  • A refused write is shown by absence at a subscriber, with a control write. Step 1 read a router log line.
  • Reading is open on cuaslab: every TLS client may subscribe to **. Step 1's stand-in had scoped reading on.
  • The goat client is the released 0.5.19 with a real context, not a source build with a hand-written profile.
  • The bridge noticed the cut after 5 s, against 9 to 10 s in step 1. Not explained.

Known limits

  • No mesh on the data path. Two VMs on one Mac, joined by a route. No WireGuard.
  • Nothing revokes a slot certificate on this path. goat cuts a machine off at the mesh, and the rig is not on it.
  • No ingress gateway. The bridge connects to the core router; a goatlite has no gateway.
  • One slot for the whole pod. See ADR 1251.
  • The recorder's class. It is enrolled as FUSION because goat has no class for a reader that writes nothing.
  • Clocks are known only to within 124 ms between the VMs.
  • Scale. One run of each check, minutes long, one pod, one Mac.
  • The programs did not change, so every limit of step 1's record still holds.

Step 4: what went wrong, and what it taught

Questions asked along the way

What stays on cuaslab

  • One machine grant: quota 5, affiliation cuaslab-lab.
  • Three machines: pod1-bridge (POD), host-fusion (FUSION), host-recorder (FUSION). Certificates are valid to 2027-11-18.
  • The portal runs with portal_bundle_create_bin: "". A fresh render from goatlite.yaml turns it back on, and enrolment then fails again.

"How to remove what step 4 left" is in docs/acceptance-goat4.md. Revoking a machine is a write to cuaslab and was never run.

Changes on the Mac and the VMs

  • NetBird installed, profile cuaslab; the Mac is a mesh peer. Always netbird up --profile cuaslab.
  • Colima: network.address: true, plus a route to 192.168.64.4 through 192.168.64.1.
  • goatlite VM: a netplan route to 192.168.64.5 through 192.168.64.1.
  • Both routes depend on net.inet.ip.forwarding=1 on the Mac.
