## What happened that the plan did not foresee

1. Lima's host agent sets the guest clock of `goathost`, apart from `systemd-timesyncd`: it reads the drift through the guest agent about every 10 s, and at boot logged `Time sync: guest clock adjusted (was 312ms off)` (`task-2-vm.txt`). A step holds only while both `systemd-timesyncd` and `lima-guestagent` are stopped, and while the guest agent is stopped the Docker socket that Lima forwards is down. The plan's `g4b_clock_step` stops both (`3904f92`).
2. In the trial, the restore at first relied on `systemd-timesyncd`, whose first NTP synchronisation stepped the clock back (`task-3-clock-step-trial.txt`). `87ef147` made the restore undo the sum of the steps itself, and wait until both services are active and the offset is that of before.
3. `g4b_vm_sync`, run while the host services ran, left `host-fusion` with its working directory outside its mount; the function now refuses (see "The VM and the gate").
4. macOS `tar` put extended attribute headers in the stream to the VM, and GNU `tar` in the VM warned on each; `g4b_vm_sync` now sends none (from the task report and `bc72f1f`).
5. The variable `${LIMA_CIDATA_USER}` of the provision script made Lima 2.3 warn on every call; the VM was made a second time with `{{.User}}`.
6. Colima and `goathost` could not reach each other, so the drop rule that the plan held ready was not needed (G4B-02).
7. The natural clock difference was a few milliseconds, so the clock was not disciplined, and the extra offset of -0.5 s that the ledger of the plan had ruled for a disciplined clock was not added to G4B-06.
8. The clock trial made the pod drop 4 of the host's tasks, `fusion-node-1  | 12:43:11 fusion: invalid message from above dropped: (root) (message timestamp reasonable): Timestamp delta 0:00:00.493293 > 0:00:00.100000` among them (`task-3-clock-step-trial.txt`).
9. The controlling session restarted during Task 3's run of G4B-04, and the task was resumed; one evidence file holds a partial first section (see "Runs and evidence").
10. The host answers each message it rejects with an Error to the pod, so at the offsets where the host rejects the pod's messages most of the down traffic is Errors (G4B-06).

## Known limits

From the design, section 9, with what the runs added:

- **The four points of `docs/goat-context.md` gap 14.** Step 4b changes none of them. The pod's machine is not a mesh peer (ADR 1092); nothing can cut a machine off (ADR 1025, ADR 1031); the sensors and the pod fusion node have no fabric identity (ADR 1122); every source appears as the pod (ADR 1251). The first two cannot be met on a goatlite, where the router listens on the LAN and the box is not a mesh peer.
- **One Mac.** The three VMs share the Mac's clock source and its network stack, and the Mac routes every packet between them. A clock difference was set by hand, not met in the field; the difference that step 4 warned of, near 100 ms, was not seen between Colima and `goathost` (G4B-05).
- **The path between the pod and the host is closed by vzNAT, not by the rig** (G4B-02). Nothing checks that it stays closed.
- **The keys.** `zenoh/goat4/pki/` on the Mac holds all three keys, and the pod's containers get theirs by a bind mount from it. Step 4b keeps the pod's key out of `goathost`; the two host keys are now on the Mac and on the disk of `goathost`.
- **Reading is not limited on `cuaslab`,** and all the limits of `docs/acceptance-goat4.md` that concern the programs remain, because no program changed.
- **Two helpers, one project name.** `dg4` of step 4 and `dg4b_pod` act on the same project `apex-goat4`. `goat4b_ready` fails if a host service of `apex-goat4` runs in Colima, but nothing stops `dg4 up -d` while the step 4b rig runs.
- **The helpers' guards.** `dg4b_pod` and `dg4b_host` find the subcommand as the first word that is not an option, so a global option with a separate value before `up` (for example `--profile join up`) is not seen as `up` and not checked (from the review of Task 1; nobody uses that form).
- **The run scripts.** `goat4b/run_lib.sh` sources the agent session's git-ignored Docker environment file; on another Mac zsh should print one error line and go on (tried with a scratch script in Task 6, not saved; the scripts were not run without the file). The clock state file is in `/tmp`. The traps that restore a route were not shown by an interrupted run; the clock trap was (G4B-06).
- **The scale of the evidence.** One task run of each check, of minutes, on one Mac. The README run repeated G4B-01 to G4B-04 once.

## How to remove it

None of this was run.

- **Everything at once.** From the repo root: `. goat4/dg4.sh; . goat4b/host-vm.sh; . goat4b/dg4b.sh`, then `dg4b_host down`, `dg4b_pod down`, and `g4b_vm_remove --yes`. It removes the route and the route file on `goatlite`, then stops and deletes `goathost` with its disk, and with it everything listed for `goathost` above (from the source of `goat4b/host-vm.sh`; never run). Without `--yes` it prints what it would remove and changes nothing (from source and a unit test).
- **By hand, on `goatlite`.** `limactl shell goatlite sudo ip route del 192.168.64.6/32` and `limactl shell goatlite sudo rm -f /etc/netplan/92-goathost-route.yaml` (`task-2-goatlite-change.txt`; not run). If `goathost` was made again with another address, the route names that address: `g4b_routes_check` prints it.
- **Then** `limactl delete --force goathost` removes the VM (from the source of `g4b_vm_remove`; not run).
- Nothing needs to be removed from Colima or from `cuaslab`.
